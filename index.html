Benchmarks

A benchmark is a fixed set of tasks plus a fixed way of scoring, so two robot policies can be compared fairly. These eight test very different things. Pick a tab; each one is built to be understood in about 30 seconds. Dotted words explain themselves when you hover or tap them.

The loop every benchmark measures

Every task here is the same loop, repeated many times a second until the episode ends. Benchmarks differ in what the world looks like, what data you get to learn from, and how success is counted.

One timestep of data

Each demonstration is a recording of this loop, dozens of times per second. A policy learns to copy the action given the observation (imitation learning). Since July 2026 the composite datasets also label every frame with its sub-task, skill name and instruction.

  • Proprioception: arm joint angles, gripper opening, base position

Atomic skills: the building blocks

An atomic task is one short skill. RoboCasa365 has 65 of them, covering ten skill families: pick and place, doors, drawers, knobs, levers, buttons, insertion, navigation, sliding racks, and lids.

Composite tasks: real chores

A composite task chains several atomic skills into something a person would actually ask for. The task list was drafted with help from an LLM (GPT-4) so it reflects common household activities. These are long-horizon: many steps, but everything stays visible.

Different robot bodies

RoboCasa supports several embodiments: single-arm mobile robots, humanoids and quadrupeds with arms. The action vector depends on the body. The arm and gripper part stays similar, but the base, torso and mode slots above are specific to PandaOmron.

How it's scored

Success rate per task, averaged over task groups. RoboCasa365 is set up for three settings: multi-task learning, foundation-model training, and lifelong learning. A public leaderboard (live since April 2026) compares community submissions. Note: v1.0.1 raised every task's time limit by 1.5×, so use the latest version when comparing numbers.

Why it exists

Most robot tasks are Markovian: the current camera frame shows everything you need. In MIKASA the key fact is shown once and then hidden, so a policy that only looks at the present frame can do no better than guess. Long is not the same as memory. A RoboCasa chore can take hundreds of steps without needing any memory.

How it's scored

Success rate, reported per horizon split with fixed seeds: Short (38 tasks, 25–200 steps, 1–8 s), Medium (30 tasks, 201–600 steps), Long (22 tasks, 601–2,160 steps, up to 86 s). The original RL-only release had 32 tasks and 4 memory types; it's still on the mikasa-robo-rl branch.

The four suites

Robots need two kinds of knowledge: declarative (what objects are and where they are) and procedural (how to move). The first three suites each change only one thing, so you can see which kind of knowledge transfers.

LIBERO-Spatial · 10 tasks

Same objects, different layouts. Tests spatial relationships.

"pick up the black bowl between the plate and the ramekin and place it on the plate"

LIBERO-Object · 10 tasks

Different objects, same layout. Tests recognising objects.

"pick up the alphabet soup and place it in the basket"

LIBERO-Goal · 10 tasks

Same objects and layout, different goals. Tests behaviour.

"open the middle drawer of the cabinet"

LIBERO-100 · 100 tasks

Everything varies at once (entangled). Split into LIBERO-90 for pretraining and LIBERO-10 for longer test tasks.

The 2-minute explainer

Official LIBERO intro video: how tasks are generated from human activities, the four suites, and the main findings. Its scenes are high-quality renders made for the video; the simulator frames above are what the policy actually sees.

How it's scored

In the lifelong setting, tasks arrive one at a time. LIBERO reports forward transfer (FWT), negative backward transfer (NBT), which measures forgetting, and area under the success curve (AUC). Most VLA papers skip the lifelong part and simply report success rate on each suite after training on all of them together.

State of the art

The number everyone reports is multi-task success rate (%) on each of the four 10-task suites after fine-tuning on their demos, averaged over 500 episodes per suite. By this measure LIBERO is essentially saturated.

Action · 17 numbers (cap gripper)

r11r12r13x0–3 r21r22r23y4–7 r31r32r33z8–11 000112–15 · always grip16
  • r is a 3×3 rotation matrix and x y z a position in metres. Together they make a 4×4 homogeneous transform, flattened row by row into slots 0–15.
  • Why "0 0 0 1"? The bottom row is always that constant, so it carries no information. It's there so poses can be chained by plain matrix multiplication. Only 12 of the 16 numbers are free, and r must be a valid rotation.
  • Which frame? With delta (the default), the matrix is expressed in the gripper camera's own frame: the target is camera_pose @ action, so "x = 0.02" means 2 cm along the camera's x-axis, wherever it is pointing. With absolute, it is the target camera pose in the MuJoCo world frame, the same frame as camera_pose.
  • grip is a command in [0, 1].

The droid arm uses a different action: 7 joint angles + gripper (8 numbers). In delta mode these are added to the current joint angles.

Where the policies come from

EgoGym was released with Contact-Anchored Policies (CAP). CAP learns from real-world human data collected with a handheld gripper, then runs in EgoGym with no extra training. These clips show that real-world data. It is not part of EgoGym; it shows what the evaluated policies learned from.

How it's scored

Success rate over many randomised episodes (1,000 by default). An episode succeeds when the reward crosses a threshold. In the code's defaults that is a lift over 5 cm for Pick and 0.5 for Open. Optional unprivileged wrappers use a vision-language model (Molmo, Gemini, GPT, Moondream) to find the target, so the policy never gets hidden simulator information.

State of the art

EgoGym is new (Feb 2026), and the only published numbers so far are from the CAP paper, on EgoGym-Pick. Both policies run zero-shot: neither was trained in EgoGym.

RoboTwin 2.0

A robot with two arms learns 50 tabletop tasks in clean scenes, then must do them in cluttered, re-lit, re-textured ones it has never seen.

Benchmark type
Bimanual benchmark + automatic data generator, for imitation policies and VLAs
The world
A two-armed robot at a table, simulated in SAPIEN (the engine under ManiSkill3), not MuJoCo
The data
100,000+ demonstrations from scripted experts, not humans
The tasks
50 tasks with 731 objects in 147 categories, 5 robot bodies

Video: a real handover_block demo from the RoboTwin dataset. Left: the fixed head camera the policy sees. Right: the left and right wrist cameras. Played at the dataset's 30 fps, about 1.8× real time.

One timestep of data

Nobody teleoperates these demos. Each task has an expert program (first drafted by an LLM, then fixed using feedback from simulation), and a motion planner runs it to make as many successful episodes as you want. A policy then learns them by imitation.

Observation

  • Three RGB images (320×240 by default): a fixed third-person camera (head_camera, fixed in the world where the robot's head would be, above and behind the arms, looking down at the table) and two wrist cameras (left_camera, right_camera)
  • Proprioception: both arms' joint angles and gripper openings (qpos), plus each gripper's pose (endpose)
  • A language instruction, e.g. "Pick up the red block using the left arm, give it to the right arm". Instructions are generated from templates in many phrasings, and the hard test uses phrasings kept out of training
  • Optional depth and point clouds (used by 3D policies like DP3)

π₀, π₀.₅, RDT, ACT, DP, DP3 baselines; world-action models

Action · 14 numbers (aloha-agilex, qpos)

L j1L j2L j3L j4L j5L j6L grip R j1R j2R j3R j4R j5R j6R grip
  • 0–5, 7–12 · joints. Absolute target angles (radians) for the six joints of each arm, left arm first. Not deltas, and not a gripper pose.
  • 6, 13 · grippers. Opening ratio in [0, 1]: 0 closed, 1 open.
  • One action = one waypoint. The simulator plans a smooth path to the target and runs physics at 250 Hz until it gets there, so a step is not a fixed slice of time. Recorded demos keep one frame every 15 physics steps (0.06 s).

The other mode, ee, sends 16 numbers: per arm, the gripper position x y z plus a quaternion (w, x, y, z), both absolute in the world frame, then the gripper. qpos length depends on the robot (a 7-joint Franka arm gives 8 per arm); ee is always 16.

Tabletop jobs for two arms. Some need both arms at once (lifting a pot by both handles, handing an object over). Others use whichever arm is closer, so the policy also has to pick the arm. Episode limits range from 400 to 1,500 actions.

Clean vs randomized

This is the heart of the benchmark. The demo_clean setting is a plain white table. demo_randomized applies domain randomization along five axes: distracting clutter on the table, random background and table textures, random lighting, table height (up to 3 cm) and unseen instruction phrasings.

Different robot bodies

Five embodiments: the default aloha-agilex (two 6-joint arms on one platform), plus ARX-X5, Piper, Franka Panda and UR5 with a WSG gripper. Single-arm robots are placed as a left and right pair, and the pair can be mixed, e.g. a Piper next to a Franka. The expert programs adapt to each body, so the same task can generate data for all five. The leaderboard uses aloha-agilex only.

How it's scored

Success rate over 100 episodes per task, averaged across the 50 tasks. Policies train on 50 clean demos per task (2,500 total), then are tested in two settings. Easy (clean → clean) tests in the same kind of plain scene. Hard (clean → randomized) tests in randomized scenes with unseen instructions. The leaderboard ranks by the average of the two, and separates "co-train" (one policy for all 50 tasks) from "single" (one checkpoint per task).

Multi-task · few-shot · vision-guided manipulation

RLBench

One Franka arm, 100 hand-built tasks, and as many perfect demos as you ask for. The long-running test of precise, multi-task manipulation.

Benchmark type
Benchmark + learning environment for imitation, RL, multi-task and few-shot learning
The world
A Franka arm at a wooden table, simulated in CoppeliaSim through PyRep. Not MuJoCo or SAPIEN
The data
Unlimited demos, made by a motion planner following hand-placed waypoints
The tasks
100 tasks, each with language variations. Most papers use a standard 18-task subset

Video: a real open_drawer demo ("open the middle drawer") from the standard 18-task dataset at the real 20 Hz. Left: front camera. Right: left shoulder, right shoulder, overhead, wrist. Each view is 128×128, shown enlarged.

One timestep of data

RLBench gives you the whole robot state and five cameras, and lets you choose the action space. The widely used setup (from PerAct onward) doesn't predict every 50 ms step. It predicts the next keyframe, a gripper pose where something important happens, and lets a motion planner drive the arm there.

Observation

  • RGB, depth and segmentation masks from five cameras at 128×128. Action · 8 numbers (keyframe pose)

xyzqxqyqzqwgrip
  • 0–2 · position of the gripper tip in metres, absolute, in the world frame (EndEffectorPoseViaPlanning).
  • 3–6 · orientation as a unit quaternion in (x, y, z, w) order, PyRep's convention. RoboTwin uses (w, x, y, z), so check before converting.
  • 7 · gripper: Discrete, > 0.5 open, < 0.5 closed.
  • One action = one whole move. The planner finds a collision-free path and runs it before step() returns. PerAct-style agents add a 9th number, "ignore collisions", so the planner can touch objects when it has to.

Other modes: JointVelocity (7 joint velocities + gripper = 8, used in the README examples), JointPosition, JointTorque, and EndEffectorPoseViaIK. Pose modes can also be delta or relative to the gripper's frame.

How the demos are made

Each task is a CoppeliaSim scene plus a short Python file. The author places waypoints (where the gripper should go, in order) and a success sensor, and codes how objects are randomised for each variation. The motion planner then turns waypoints into as many demos as you want, so there's no human teleoperation and no limit on data. The official tutorial below builds slide_block_to_target this way.

How it's scored

Success rate: every success condition the task registers (usually a proximity sensor detecting the right object in the right place) must hold before the step budget runs out. The standard multi-task protocol (introduced by PerAct): train one policy on 100 demos per task across the 18 tasks, then test 25 episodes per task with a budget of 25 keyframe steps (35 for place cups and stack blocks). Report the mean over the 18 tasks, usually averaged across five evaluation seeds. Only the Franka arm counts for benchmarking, even though Mico, Jaco, Sawyer and UR5 can be swapped in.

Action · 7 numbers (ee mode)

xyzrollpitchyawgrip
  • 0–2 · position of the gripper in metres, absolute. The bundled policies measure it from the robot base, i.e. world axes with the base position (0, −0.4, 0.78) subtracted.
  • 3–5 · orientation as Euler angles, xyz order, in radians. The state uses a (w, x, y, z) quaternion, and the adapters convert between the two.
  • 6 · gripper: ≥ 0.1 → open (fingers at 4 cm), otherwise closed.
  • One action = one control step. The evaluator solves IK for 7 joint angles and applies them for one environment step (100 physics substeps). Policies usually predict a chunk of such poses and replay them.

Under the hood env.step takes 9 numbers: 7 absolute joint angles + 2 finger positions. A joint control mode lets a policy output those directly. LeRobot's wrapper exposes the 7-number pose action, scaled to [−1, 1].

Composite tasks

Long-horizon chores (long-horizon) that chain several skills and often need a plan first: sort objects into groups, make coffee, set a study table for a given subject, or answer a word problem by arranging number cubes.

How it's scored

Evaluation uses fixed episode files grouped into tracks. Each track has 10 primitive tasks × 50 episodes and changes one thing. Track 1 is in-distribution. Track 2 uses unseen object categories and instances. Track 3 uses common-sense descriptions of the target. Track 4 uses semantically rich instructions. Track 5 is open cross-task transfer. Track 6 uses unseen textures. Three metrics: success rate; progress score, the fraction of sub-conditions met (a correct grasp counts); and intention score, whether the gripper got within 10 cm of the right object even if it failed. A separate VLM track asks language models to plan skill sequences. Episodes are capped at 200 policy steps by default.

LIBERO-Plus

The same 40 tasks as LIBERO, but each one is nudged: the camera moves, the arm starts elsewhere, the lights change, the words are reworded. Models scoring 95% on LIBERO fall apart.

Robustness stress test for VLA models (CVPR 2026). It's a drop-in replacement for the libero package

Identical to LIBERO: a Franka arm in robosuite 1.4 on MuJoCo, plus new objects, textures and camera poses

Train on ordinary LIBERO demos, or on the optional 14,347-episode set that already contains perturbed scenes

The seven perturbations

Each variant changes one factor from an original LIBERO task and is tagged with a dimension and a difficulty level from 1 to 5. The counts come from the benchmark's task_classification.json. Every clip below is a real failed rollout of OpenVLA-OFT, a model that scores about 97% on plain LIBERO.

Two ways to run it

LeRobot: --env.type=libero_plus

Built into lerobot-eval. Install the LIBERO-Plus fork, which replaces vanilla libero in the same environment, then evaluate any LeRobot policy on libero_spatial, libero_object, libero_goal or libero_10. Training data: lerobot/libero_plus (20 fps, 256 px front + wrist).

lerobot-eval --env.type=libero_plus --env.task=libero_spatial,libero_object,libero_goal,libero_10

Socket server: simulation_libero_plus

A fork that runs the simulator as a ZMQ server, so the policy can live on a separate GPU machine. It sends both images (256 px, upright), the gripper pose, the instruction and a timestep. It gets back a 7-number action, runs environments in parallel batches, and writes success broken down by suite, dimension and difficulty.

python -m versatil_inference.run_evaluation --task_suite_name libero_plus_spatial

How it's scored

Success rate, with the same success check as LIBERO. The full protocol runs one trial per variant, since each of the 10,030 variants is already its own task, and reports the total plus a score per perturbation dimension (and per difficulty level). The socket server caps episodes at 600 steps. LeRobot's quick protocol instead runs 10 episodes per task over the four suites, with LIBERO's per-suite step limits. Compare numbers only within one protocol.
